## Problem, affected parties and intended outcome

Max identified two independent efforts in this repository:
[MCP modernization (#25)](https://github.com/Hadden-Industries/universal-ontology/issues/25)
and [SHACL policy source of truth (#31)](https://github.com/Hadden-Industries/universal-ontology/issues/31). Separate Git worktrees already provide separate
working files and local SDLC evidence. The method does not yet make the coordination
between these executions explicit enough for another author to discover overlapping
contracts, shared mutable resources, integration responsibility or the combined
revision that was actually checked.

The intended benefit is understandable, reliable parallel work using the existing
SDLC. Authors should continue independent changes while surfacing real dependencies
and decisions. Acceptance must establish the behavior of the integrated result.
Routine progress, another active task or an architectural checkpoint alone should
not require a pause.

## Scope and terminology

An **execution** is one routed task operating on one physical worktree and its
local evidence. A **shared resource** is mutable state that worktree separation
does not isolate, such as a common environment, fixed port, external cache,
published channel or Git common configuration. An **integration target** is the
actual combined source state intended for acceptance, identified by Git revision
and any relevant uncommitted inputs. An **integration owner** coordinates that
target and its evidence; this is a responsibility, not an additional agent role.

Each physical checkout permits one independent implementation execution. Independent
tasks need separate worktrees even when they expect to edit unrelated files; local
task state, verification records and the Git index belong to the whole checkout.
Coordinated pairing within one task is still one execution. Overlapping logical
files or configuration changes in separate worktrees require coordination and
integration evidence, not concurrent ownership of the same physical copy.

Apply the extension in Universal Ontology first. Preserve the deployed 1.0.0
pre-release status and existing host/command protections. Do not build a central
scheduler, global task database, general shared lock service or cross-repository
distribution mechanism. A bounded guard for exclusive native task creation in one
checkout is in scope; a multiwriter scheduling or ownership framework is not.
Do not enable a merge queue, change branch protection,
install dependencies or adopt another host as a side effect. Those would require
separate evidence and exact approval if a real need arises.

The current MCP and SHACL implementations continue under their existing accepted
scope. This proposal does not retroactively invalidate their approvals, change
their files or assign them to new writers. At the original observation, the SHACL
worktree was at `36a51ff4...` with its proposal documents staged and no native active
implementation record. This is historical context, not its current execution status.

REQ/AC-008 hardens the existing single-execution boundary against accidental
competing starts. It does not permit multiple independent tasks in one checkout or
prevent arbitrary processes from editing files outside the native SDLC commands.

preserve established ownership and evidence, and make any incomplete acquisition
actionable without silently taking over an existing task. This is bounded local
failure handling, not automatic scheduling or general lock recovery.

## Native capability assessment and bounded direction

Git already separates worktree files, HEAD and index while sharing ordinary refs
and common configuration. Use its supported worktree inventory and path-resolution
commands; do not infer common/per-worktree paths by string substitution.
[Git worktree documentation](https://git-scm.com/docs/git-worktree).

Existing per-worktree lifecycle records and native fingerprint validation supply
the local control. Existing PR CI supplies candidate checks; its per-ref concurrency
setting prevents redundant runs for the same ref, not conflicting changes across
different tasks. The `pull_request_target` SDLC job checks trusted baseline/metadata;
it does not execute the candidate's product implementation. No current branch-rule
or merge-queue qualification was performed for this proposal.

GitHub's native merge queue can check changes with the current base and earlier
queued changes, but requires suitable checks and `merge_group` workflow support.
It is an option if later integration evidence justifies it, not a selected
configuration change here. The current inspected MCP workflow has no `merge_group`
event. [GitHub merge queue documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).

**Accepted direction, subject to the detailed implementation baseline:** add
explicit coordination/handoff rules, meaningful linked-worktree regressions and
exclusive-start evidence/repair within the existing single-active-task model.
Establish a reproduced requirement violation before changing runtime behavior.
Leaving the method unchanged retains implicit coordination and the automated
coverage gaps. Supporting independent tasks in one checkout would require shared
index, evidence and file-ownership coordination without a demonstrated benefit for
this use case. Separate worktrees remain the supported approach.

This maintenance proposal introduces no selected third-party component. Git, Node,
npm and Python use the repository's existing approved toolchain. It does not claim
a new latest-version or licence qualification. Refresh relevant supported native
interfaces before implementation; any new adoption or material integration needs
the normal REU-01/VER-01/LIC-01 research and exact configuration decision.

## Risk route and acceptance boundary

**Risk class:** R0 for preparing and publishing this proposal; proposed R2 for implementation
of material concurrent lifecycle/handoff behavior. R2 is justified by concurrency,
cross-task workflow and verification-evidence retention, not by document size.

**Decision owner:** Max.

**Reasoning:** Incorrect ownership or integration evidence can affect multiple
accepted tasks; a targeted procedural/test extension bounds that risk. No R3
consequence is established by the current evidence.

**Potential blast radius:** Universal Ontology contributors, local verification
records, review decisions and the first combined integration. No cross-repository
adoption is in scope.

**Reversibility:** The proposed documentation/tests are reversible; retain all
native evidence and active task state. Any discovered state migration or destructive
recovery need must be separately routed before implementation.

**Principal unknowns:** Actual future shared-resource use; semantic overlap at
integration time; branch-rule enforcement; behavior of real linked-worktree fixtures
on supported platforms; the reproduced competing-start behavior and smallest native
exclusive-creation mechanism, including failed/interrupted-start handling.

**Required artifacts:** This Issue, its protected R2 baseline after actual acceptance,
and a thin executable plan reflecting the exact approved change. Reuse existing
task/evidence records rather than duplicate authorities. Keep any necessary plan
in this Issue unless unresolved material design or coordination warrants a separate
artifact; no second maintained copy of this proposal is required.

**Required specialist lenses:** Independent lifecycle verification; focused
operability review of evidence retention and resource ownership where material.
No automatic additional agent or security scan is authorized by this proposal.

**Required verification:** Meaningful linked-worktree native CLI tests, relevant
negative controls, controlled same-checkout competing-start tests, consumer schema

**Required human approvals:** Accept requirements/route; approve exact policy,
