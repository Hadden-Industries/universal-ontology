## Problem, affected party and desired outcome

Improve the existing local Universal Ontology MCP server so a competent JavaScript/
Node author unfamiliar with repository conventions can locate transport setup,
trace a tool into ontology-query behavior and find the checks needed for an SDK
update. Alignment with applicable current best practice is itself an accepted
benefit; no measured maintenance saving or prior incident is required.

Preserve the higher product outcome: search for Person, resolve the exact entity,
return the authored lexical definition and immutable release provenance, and
distinguish assertions from inference. Shared website, WebMCP, artifact-production
and distribution consumers must retain their accepted behavior.

Max accepted the concrete design on 2026-09-08 in the originating Codex task:
"This concrete design captures what I want - proceed". This followed presentation
of MCP improvement dossier revision 6 and implementation-plan revision 1. The
design interview is complete; implementation, configuration and remote/Git gates
remain distinct. This Issue body transcribes the accepted requirements and design
so its eventual baseline snapshot is self-contained. It does not claim a baseline
has already been captured/merged or that implementation evidence has passed.

## Accepted architecture and decisions

- **DEC-001:** Improve the existing local server; publication and hosting stay
  outside scope.
- **DEC-002:** Preserve the inherited modern/native-legacy stdio and loopback HTTP
  boundaries. Use actual-era checks and the independent real-query oracle. Reuse
  affected existing package, host, archive and OCI obligations without inventing
  new support promises.
- **DEC-003:** Use the existing `packages/universal-ontology-mcp-server` workspace
  for MCP development, plus private `packages/universal-ontology-query` and
  `packages/universal-ontology-projection-policy` workspaces for their actual
  consumers. The projection policy owns release-specific RDF property selection,
  historical assertion preservation and bounded historical-source interpretation;
  website rendering consumes it directly. Root owns website/index/channel production,
  cross-product verification and installer/distribution orchestration.
- **DEC-004:** Retain native `serveStdio`, `createMcpHandler`, protocol validation,
  stateless legacy operation and JSON terminal responses. Use released native
  representation handling; reuse `isJsonContentType` if a justified early check
  remains. Each real ingress owns its raw-byte bound once. Node's supported
  `parsedBody` composition may reuse a value whose original stream was bounded;
  the standalone Fetch contract remains bounded independently. Remove duplicate
  buffering only with evidence. A native conformance gap requires replanning.
- **DEC-005:** Align MCP metadata authority with its workspace manifest and preserve
  existing artifact/Registry validation. No schema bump or metadata generator is
  selected merely for freshness or uniformity.
- **DEC-006:** Keep existing safe diagnostics and protocol/stderr separation;
  defer a new protocol-logging capability without a real support use case.
- **DEC-007:** Applicable best-practice alignment is sufficient value. Include
  safer SDK updates and maintainability for unfamiliar competent JS/Node authors;
  measured time savings are optional corroboration, not an admission gate.

Query interfaces expose the existing query factory/error identities at root,
schemas at `/schemas`, artifact construction/parsing/canonical/digest/path contracts
at `/artifacts`, and separate same-origin Fetch, filesystem and persistent HTTP
repository entries. Keep Node modules out of browser imports and preserve cross-
package error identities. Move the actual JSON deep-freezing implementation from
the schema module into `/json-value-immutability`, document its validated acyclic
JSON preconditions and use native `Object.freeze` for the flat displayed-release
context. No arbitrary object-graph or arbitrary-schema compatibility API is added.

Projection-policy data remains one authored declaration/schema. Preserve schema
IDs, format versions, delivered bytes and `/ontology/projection/` URLs through the
website's existing copy/collision controls.

The MCP package remains CLI-only. Its source/build/test dependencies are development
dependencies used to produce the existing self-contained bundle. The installed
tarball requires Node, without private workspace dependencies, unshipped source
exports or install-time compilation. Retain explicit build/prepack and existing
engine support. Move private MCP source/tooling consumers with their owner; root
orchestration invokes actual operations rather than keeping obsolete forwarding
source paths. Retain bundle input restrictions, exact component attribution,
embedded dependency inventory, full notices and provenance.

## Software-selection research and adoption restrictions

Primary-source/repository comparisons are recorded in dossier SRC-009 through
SRC-014 and EVD-003 through EVD-005. They compared retaining root source ownership,
native workspace ownership/shared interfaces, released SDK configuration/composition
and broader maintained HTTP middleware. The accepted choice uses npm workspace
dependencies/scripts and Node explicit exports, with the current SDK's supported
protocol handling and the residual application admission/raw-byte controls.

On 2026-09-08 the official registry selected server/node/client SDK 2.0.0, released
from `cc4b41617ce3601b1290d67216ea0b194a3cd9ac`. Its public Content-Type helper is
available; configurable request-body limits documented in later source were added
after that release and are unavailable through a released update. Hono body-limit
middleware was considered but not qualified for the complete existing raw-ingress
and rejection contract; no new framework, fork, shim or prerelease adoption is selected.

Preserve the SDK's exact Apache-2.0/MIT transition and documentation terms rather
than relying on its short registry MIT label. The installed SDK's embedded
fast-uri 3.1.0 remains governed by the existing adoption assessment: no new untrusted
JSON-schema ingress, elicitation, validator injection or broader URI authorization/
fetch boundary is authorized. Existing source continuity is not a new security
verdict or upstream repair. Refresh current stable/applicable supported LTS and
exact rights at execution, and retain accurate embedded component notices.

Zod Classic is applicable to these fixed domain schemas; generic library guidance
does not require a standalone import-spelling change or new arbitrary-schema support.
Native registry checks also matched the already-installed Jest/@jest/globals
30.5.1, esbuild 0.28.2 and Zod 4.5.4. Proposed dependency ownership changes preserve
