## M701 — `docs/sdlc/proportional-workflow.md`

Append this section after the existing content. This is the canonical owner of the new cadence rule; the remaining amendments refer here rather than duplicating the whole procedure.

```markdown
## Execution cadence and evidence placement

Use one short execution statement in the existing accepted task or PR: current
deliverable and non-goals, material risks, one representative consumer outcome,
actual required checks, rerun triggers, external capability dependencies and
concrete stop/decision conditions. For R0/R1, a few sentences normally suffice.
Do not create an Issue, matrix or separate baseline merely to record cadence.
Every mandatory activity must follow accepted intent, an applicable governing
rule or an explicit decision for a concrete risk. Do not turn a recommendation
into an existing acceptance condition or reopen settled choices at every milestone.

Risk determines required assurance, not the frequency of the same check. Use
focused checks during editing, affected consumer checks at meaningful integration
points, and the actual required full profile and independent obligations on the
final frozen elevated-risk object. A focused run inside an R2 task does not lower
its risk, complete it or move the start of its accepted scope. Do not split or
restart executions merely to evade accumulated obligations.

Identify actual command composition before claiming duplicate work. A native
command may already execute another requested check; its current result can
satisfy that same obligation where the accepted contract permits. Do not skip a
separately configured required row, relabel a receipt, or substitute the writer's
run for independently required execution. Profile names alone do not establish
coverage of mutation, packaging, native host behavior or release qualification.

Keep raw results in their native evidence store. Put current progress in an
authorised task/PR comment or retained operational handoff location, not repeated
appends to a tracked execution diary. Preserve the diary's history and any
explicit requirement to maintain it until an amendment is accepted. Do not edit
accepted Issue text merely to record progress. Keep native receipts and active
state with their native writers; retain required evidence before worktree release.
An ignored local file is not automatically durable storage.

Accepted requirements, fixtures, executable examples and agent/security
instructions remain real inputs, including when written in Markdown. Promote a
useful durable summary deliberately before final freeze and retain historical
results with their original identities. A later tracked edit or HEAD change still
requires the applicable fresh evidence under the current gate. Do not add blanket
Markdown exclusions, ignore/index tricks, a result cache or a stale-pass exception.
A more selective reuse contract requires a separately accepted design and positive
invalidation tests for its actual source, oracle, dependency, environment and
control inputs.

After a fix, review the affected questions against the earlier reviewed object
and actual delta; widen scope where the risk or uncertainty requires it. Use the
normal correctness/principles review plus the justified specialists, not a default
role fan-out. Preserve existing security triggers, native workflow ownership,
budgets and mandatory independent assurance. Failed or unavailable workers remain
evidence gaps. Stop implementation edits before independent verification.

Exercise the representative user outcome at the first stable usable seam and
recheck the materially affected delivered boundary at final qualification. A
build, HTTP success, development server or test total is not the requested
installed/built/native outcome. An early failure is useful evidence, not product
acceptance. Use already accepted representative inputs and independent oracles;
do not invent new product scope or replay a historical project to test the process.

Observe pauses, rerun causes, check composition, causal findings, retained-resource
ownership and actual user outcomes through existing records. Separate elapsed
critical path from overlapping job durations. Do not create mandatory telemetry,
claim an unmeasured saving or require numerical savings to accept a justified
improvement. If an essential transition or capability is unavailable, preserve
state and report the exact decision needed; do not invent a command or waiver.
```

## Questions and bounded follow-up

Before dispatch, identify the unresolved question, affected object, required evidence
and why existing accepted work does not answer it. A role's availability is not a
requirement or permission to spawn it. Use the ordinary combined review and the

counterevidence, and follow the existing evidence/consumer-release procedure.

change neither the autonomy ceiling nor the authority to install tools, amend
